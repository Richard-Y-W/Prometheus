# Threat model

## Current Program 01A boundary

Program 01A v2 protects one checked-in synthetic fixture as it crosses local artifact ingestion, relational draft review, publication, immutable object storage, API export, and independent C++ byte verification. It does not fetch remote documents, execute supplied code, invoke a solver, or decide whether an engineering project works.

The protected integrity claim is narrow: a sealed revision identifies the exact reviewed input bytes under the declared schema and canonicalization policy. It is not a claim that the source is truthful, the model is complete, the input is applicable, physical behavior is validated, or an engineering result passed.

## Threats, controls, and residual risk

| Threat | Current control | Residual risk or limit |
| --- | --- | --- |
| Duplicate-key smuggling, including escaped keys that decode to the same text | V2 JSON middleware preserves and checks raw request semantics before model parsing; duplicate decoded keys, malformed JSON, invalid UTF-8, and BOM input fail closed. Canonicalizers in Python and C++ also reject duplicates. | This policy applies to `/api/v2` JSON mutations and the package verifier, not every historical route or arbitrary future file format. |
| Unicode identity substitution | Fixture identity is an exact supported ASCII token; lookalikes create no rows. UUIDs, hashes, schema IDs, capability IDs, and field names use closed ASCII/lowercase forms. Canonicalization preserves Unicode rather than normalizing it, and tests prove NFC and NFD remain distinct identities. | Human-readable provenance, notes, filenames, and paths may contain Unicode. UI presentation must not imply that visually similar strings are identical or trusted. |
| Source path traversal, symlink substitution, or time-of-check/time-of-use races | Local ingestion confines an absolute path to a non-symlink allowed root, rejects symlinked components, opens read-only with no-follow support, compares path and descriptor device/inode/mode/size/time before and after the bounded read, verifies the expected hash, and copies bytes before persistence. | Platform and filesystem semantics still matter. The current source is a checked-in local fixture; general removable, network, archive, and hostile-filesystem intake belongs to Program 02. |
| Source mutation after ingestion | Artifact bytes are copied into immutable storage and package compilation reloads and verifies stored bytes rather than the original path. | SHA-256 is not proof that the original source was authoritative. The fixture is explicitly synthetic and unvalidated. |
| Stale review or review transferred to changed content | Review names a stable claim ID, stores the finalized claim fingerprint, and supplies `expected_draft_version`. The service locks the revision, validates the complete batch, appends events atomically, and increments the version once. Publication recomputes fingerprints and requires effective accepted reviews. | A human can still accept a wrong but unchanged claim. `reviewed_by` is only a local label and is not authenticated. |
| Cross-revision or partial review | Same-revision keys and service checks bind slots, claims, evidence, selections, and events. Duplicate claim IDs, unknown/cross-revision claims, invalid notes, or any invalid decision reject the whole batch. | Database owner privileges can bypass or replace controls; this is not a multi-tenant authorization boundary. |
| Idempotency-key reuse with a different request | Fixture and publication operations bind lifetime keys to deterministic request fingerprints. Changed revision, version, schema, or fixture input returns `409 idempotency_conflict` without overwriting the earlier record. | Clients must generate sufficiently unique keys and retain the same publication key after ambiguous transport failure. Keys are not authentication secrets. |
| Lost response, retry race, or process restart | Publication stores the deterministic terminal status, body, headers, and object binding in the same commit. Same-key/same-request retries replay those bytes without recompilation; concurrent writers serialize on the revision and database constraints. | Transient database contention can still return `503`; clients must retry unchanged. Fixture-ingestion replay preserves graph identity but is not specified as byte-for-byte replay of an older mutable draft representation. |
| Failure between compilation and publication | One locked transaction covers request record, object insertion, revision binding, and stored response. Failure-injection tests cover every stage through immediately before commit and require a clean retry. | Infrastructure outside the database transaction, such as disk durability guarantees and backup policy, depends on deployment configuration. |
| Stored-byte corruption or metadata substitution | Every export and successful publication replay reloads the object, verifies closed metadata, byte length, canonical form, SHA-256, schema identity/binding, and sealed revision relationship. Failure returns an integrity error; it never becomes success. Independent C++ checks canonical bytes, hash, and supported schema identity from the same corpus. | The C++ verifier is not a full engineering-schema or physical-truth verifier. Hashes are unkeyed and do not authenticate an origin. |
| Same-hash/different-byte collision or injected hash function | When a content address already exists, artifact and published-object stores require exact byte and metadata equality before reuse. Conformance tests inject same-hash/different-byte cases and require collision errors. | This defense detects inconsistent rows even if a hash seam is faulty; it cannot make SHA-256 cryptographically stronger or defend after both comparison code and storage are replaced. |
| Direct database mutation | SQLite triggers and PostgreSQL trigger functions/check constraints enforce v2 revision shape, claim finalization, same-revision links, append-only review, artifact/object immutability, sealed revision/child immutability, closed states, timestamps, UUIDs, and hashes. Service reads revalidate critical identities. | A database superuser can disable triggers, alter schema, or rewrite rows. Program 01A assumes the application and database control plane are trusted together. |
| False reviewer attribution | The API requires a bounded nonblank `reviewed_by` label and immutable event history. Documentation and UI label it as local audit text. | There is no authentication, signature, role policy, or non-repudiation. Anyone with local API access can choose another label; it must not be presented as verified identity. |
| Publication interpreted as engineering approval | Package authority is explicitly `reviewed_input` and `input_only`; the current execution gate is blocked. Verdict, coverage, and execution state belong to the C++ decision core, which does not consume this package yet. | A downstream UI or external client could mislabel the package despite the contract. Claims must keep the non-result limitation beside integrity statements. |
| Resource exhaustion | Requests, artifacts, canonical JSON structures, strings, arrays, object members, and package size are bounded; publication and review use time-bounded database locking/retries in the supported paths. | General parsers and Open Cascade do not yet run in resource-isolated workers. A local-user availability threat is not fully contained. |
| Replacement of both application and database controls | None within Program 01A. An attacker who can replace executable code and database constraints can forge bytes, hashes, state, UI text, and replay records consistently. | Defending this case requires signed releases, trusted updates, protected keys, secure boot/attestation where appropriate, backup integrity, and an external trust anchor. These are future product-hardening controls. |

## Trust assumptions

- The local operating system, application binary, Python and C++ dependencies, and database enforcement layer are trusted as one control plane.
- SHA-256 provides content identity, not signer identity or authorization.
- The checked-in fixture hash identifies repository bytes, not a manufacturer's assertion.
- The operator reviews claims intentionally; the software cannot infer competent approval from a nonblank label.
- PostgreSQL and SQLite provide the documented transaction/constraint semantics when configured through the repository paths.

## Parsing and execution boundary

Real STEP input is untrusted. The native Open Cascade parser still runs inside the desktop process. When the adapter is absent, the controller fails explicitly and produces no geometry. Active interruption, memory/CPU isolation, archive containment, and parser crash containment remain unimplemented.

No external solver or cloud adapter exists, so Program 01A neither uploads project data nor executes solver binaries. The lack of those paths removes their current attack surface but does not validate their future design.

## Required future controls

Programs 02, 05, and 09 must add scheme/host policy, redirect and download budgets, content/signature checks, safe artifact names, archive expansion limits, sandboxed parser workers, process CPU/memory/time limits, cancellation, project-scoped authorization, authenticated reviewer identity, signed packaging, recovery, and audit records.

Source documents remain data, never instructions. Downloaded macros, CAD scripts, embedded binaries, supplied source code, and solver decks must not execute during parsing. Any future external or cloud transfer requires explicit disclosure of artifacts, destination, credentials, retention, and licensing terms.
